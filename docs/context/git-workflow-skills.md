# Git workflow skills

The old 503-line `git-workflow` skill is split into five single-purpose skills under `ai-code-agents/claude/skills/`. The `git-workflow` agent (`agents/git-workflow.md`) is a thin router; `/git` delegates to it unchanged. `skills/git-workflow/SKILL.md` is a stub that names the five so old references resolve.

All five return the same envelope: `{"skill","status": ok|blocked|needs_input,"branch","head","blocked_by":[],"result":{...},"next":[...]}`.

## Skills
| Skill | One job | Inputs | `result` | `next` |
|---|---|---|---|---|
| git-commit | commit approved groups | worktree, scope hint, `approved` | `proposed` (needs_input) or `committed`; `unstaged`, `skipped` (secret-looking files), `left_staged`; `log_tail`, `proposed_subject` on block | git-verify |
| git-verify | run checks, write stamp | worktree, `build` | `head`, `stamp`, `status`, `results` (failing commands are the entries with a non-zero `exit`) | git-push, or git-pr when already pushed |
| git-push | publish the branch | worktree, branch, `head`, remote | `pushed_sha`, `remote`, `upstream`, `new_branch` | git-pr |
| git-pr | open a PR from a pushed branch | worktree, branch, base, issue number, gate links, verify `results` | `repo`, `pr_url`, `title`, `base`, `template_used`, `loc`, `codeowners`; `body` and `command` if gh is missing | none |
| git-issue | create an issue | repo, description | `repo`, `issue_url`, `number`, `template_used`, `open_questions`; `body` and `command` if gh is missing | none |
| brain-task-sync | after a push or PR, note progress on the user's own Brain task (advisory) | worktree, `event` (push/pr), PR url, summary, `mode` (live/dry-run), `finished`, `me_person_id` (dry-run only) | `match` (none/own/other_owner/unowned/ambiguous/title_only), `task`, `candidates`, `wrote`, `would_write`, `reason`; status is ok, skipped or error, never blocked | none |

`blocked_by` holds short codes only: `detached-head`, `head-mismatch`, `no-remote`, `remote-ambiguous`, `behind`, `diverged`, `push-failed`, `unpushed`, `gh-missing`, `repo-unresolved`, `dirty-tree`, `checks-failed`, `conflict-markers`, `hook-failed`, `hook-denied`, `message-rejected`, `error`. `next` is a hint; the router decides.

## Chains (set in the agent)
- commit: git-commit; verify: git-verify; push: git-commit, git-verify, git-push
- pr, changes not committed: git-commit, git-verify, git-push, git-pr
- pr, commits exist but are not pushed: git-verify, git-push, git-pr
- pr, branch already pushed: git-verify, git-pr
- issue: git-issue

`brain-task-sync` is inserted right after every `git-push` and every `git-pr` in the chains above (so push-then-PR runs it twice, `event` push then pr), written out in the agent's routing table. It is advisory: it runs only after the previous step returned ok, never stops the chain, and its skipped or error reason goes in the report's Brain line. The existing four skills' `blocked` and `needs_input` still end the chain.

An empty `committed` list from git-commit continues the chain. git-pr reads the `results` list of git-verify's result.

`git-commit` without `approved` returns `needs_input` with the proposed groups. The agent counts the proposal as approved only when the caller's brief explicitly pre-approves committing; otherwise the caller re-invokes it with the approved groups. A `blocked` or `needs_input` envelope ends the chain and is returned as it is.

## Helper
`local-hooks/git-facts.sh` prints repo facts as one JSON object (root, branch, default branch, upstream, ahead/behind, clean, linked worktree, PR and issue template paths, commitlint, husky, lint-staged, core.hooksPath, CODEOWNERS, changed lines against the default branch without lockfiles). Pushed state: `push_remote` (pushRemote setting, else `remote.pushDefault`, else the branch's remote, else origin, else the only remote; null when none or several and no origin), `push_ref`, `pushed`, `push_ahead`, `push_behind`. `pushed` is true only when `<push_remote>/<branch>` exists; the upstream is never used, so a branch cut from any remote branch (the default branch or another) reads as not pushed until pushed. Read-only; sets PYTHONDONTWRITEBYTECODE; `--dir <path>`; a non-repo exits 2 with a JSON error. Suite: `run-git-facts-tests.sh`. Skills call it through the live path `~/.claude/local-hooks/git-facts.sh`.

`local-hooks/gh-repo.sh` (logic in `_gh_repo.py`) prints `{"repo":"OWNER/REPO","remote","branch"}` for the repository git-pr and git-issue pass as `--repo` on every gh call that takes that flag (not `gh auth status` or any gh command that takes no `--repo`): the remote `git push` would use for the branch (`branch.<b>.pushRemote`, else `remote.pushDefault`, else the branch's remote unless `.`, else origin), read from its push URL (`git remote get-url --push`, so a `pushurl` wins). OWNER/REPO for github.com, HOST/OWNER/REPO elsewhere, case kept. Exit 2 with `{"error": no-remote|push-disabled|unresolvable|not-a-repo|usage}` when the remote is missing, its push URL is a disabled sentinel (`DISABLED`, `DISABLE`, `no_push`, `no-push`, `nopush`, `none`, `off`, `/dev/null` and the like) or any value that is not a remote URL (scheme://, scp-style `host:path` or a path), reported as `push-disabled` with a message saying it is treated as disabled, or no owner/repo can be read (a path remote); the skills then return `blocked` (`repo-unresolved`) and never call gh. Reason: bare `gh` resolves its own default (for example the public `upstream` of a fork), so a PR or issue could be aimed at another repository. Read-only, no network. Suite: `run-gh-repo-tests.sh` (also counted as one result in `run-tests.sh`).

## Rules and where they are enforced
| Rule | Enforced by |
|---|---|
| No hook bypass, no force push, no push to the default branch | git-guard.sh |
| No commit in a primary checkout | worktree-gate.sh |
| No coding-agent credit in commit or `gh pr` text | `hooks/no-agent-mention.py` |
| No private hostnames, addresses or emails in text on public repos | public-repo-text-gate.sh |
| Checks pass for the current commit before push or PR create | checks-gate.sh reads the stamp git-verify writes (warn or deny by its config). `gh pr create --repo X` is exempt ONLY when the gate knows the command's directory, resolves that checkout's push remote to OWNER/REPO (`_gh_repo.resolve`), and the command has exactly one repo flag (`--repo`, `--repo=`, `-R`, `-R=`, `-Rvalue`; values of other flags such as `--title "-R x/y"` are not read) whose value is a literal (letters, digits and `._/:@+-` only) that normalises (`HOST/OWNER/REPO`, `OWNER/REPO`, https, ssh, scp, `.git`, trailing slash, any case) to a DIFFERENT OWNER/REPO. Every other case is treated as the current repository and needs a passing check record: a variable or substitution value, an unresolvable or disabled push remote, an unknown directory, an unparsable value or flag, and duplicate repo flags. `--repo` naming the current repository, which the skills always pass, is judged like a bare `gh pr create` |
| Secret files, conflict markers, secrets in staged content or the message | commit-gate.sh denies them; git-commit also skips secret-looking files and blocks on conflict markers. Commit subject format: commit-gate warns only, where the repo already follows the convention. Takes effect once the hook is registered |
| Branch pushed before PR, secrets in PR or issue text | pr-gate.sh denies (judged from `<push remote>/<branch>`); git-pr also checks `pushed` and `push_ahead`. Takes effect once the hook is registered |
| PR size cap, PR body sections, unfilled placeholders | pr-gate.sh warns (or denies by `PR_GATE_MODE`); git-pr also warns on size. Takes effect once the hook is registered |

Repository hooks (husky, lint-staged, commitlint) run once, inside `git commit` and `git push`; no skill runs them by hand. No skill edits source files.

## Templates
- `skills/git-pr/templates/pr-body.md`: used when the repo has no PR template. No AI usage section.
- `skills/git-issue/templates/issue-body.md`: used when the repo has no `.md` issue template (yml issue forms cannot be filled with `--body`). A missing acceptance-criteria section gets a marked TBD line and an `open_questions` entry; the skill does not stop to ask.

## Template rules
Both body skills keep template headings in order, except a section the template marks conditional ("only if ...") that does not apply, which is removed. No angle-bracket placeholders or HTML comments remain; a missing value becomes a `TBD:` line with a reason. Unknown issue size leaves the boxes unchecked and becomes an open question. With several issue templates the skill matches the request type to a template name or front matter, else uses the bundled one.

## Decisions
- `gh` is needed for git-pr and git-issue only. Without it they return `blocked` (`gh-missing`) with the filled body and the command to run by hand.
- The agent gets the skills through the `skills:` list in its frontmatter (the five names). Their full content is injected into its context at start. It has no Skill tool and none is needed. A name that matches no skill is skipped silently, and a skill with `disable-model-invocation: true` cannot be preloaded. `local-hooks/tests/run-agent-skills-tests.sh` guards this: it fails if a listed name has no `skills/<name>/SKILL.md` with that `name`.
- The sibling tool ports (codex, opencode, gemini, cline, hermes) still carry the old single skill.

## brain-task-sync
Source of truth for the rules is `skills/brain-task-sync/SKILL.md` (status rules are in their own section). `collect-evidence.sh` is read-only, prints `key=value` lines, always exits 0, never prints the PR body, prints `gh=no-timeout` (PR lookup skipped) when neither `timeout` nor `sleep` can bound the call, and takes the gh executable and time limit from `BRAIN_TASK_SYNC_GH` and `BRAIN_TASK_SYNC_GH_TIMEOUT` (tests use a stub). Suite `local-hooks/tests/run-brain-task-sync-tests.sh`, also counted as one result in `run-tests.sh` (the declared check).

Evidence tiers: every ref carries `strength=strong|weak` and lists all its sources (`source=pr-closes,pr-body`), strongest wins. Strong: a number in the branch name; a closing keyword (`fixes`, `closes`, `resolves`) directly before the ref unless a negation (not, never, no, without, n't forms) is within the three words before it on the same line (then weak); a task UUID from the branch or its own commits; and, only while the PR is OPEN, the PR's own number (repo from the PR url) and gh closing references. Weak: every other mention, a UUID from the PR title or body, and everything from a PR that is not OPEN. A `(#N)` squash suffix on a commit subject, merge commits and colour codes are not refs. gh is called once (`--repo` the origin repo, one `--json` list, 10 s timeout). Only strong refs can lead to a write; weak refs and title-only matches are listed as "mentioned, not written". Commits scanned are only those unique to the branch (no merges, not reachable from any other local branch or any remote-tracking ref except the branch's own upstream), at most 50 (`commits=skipped reason=too-many` above that); a branch with a child branch scans nothing, which fails safe.

Writes go only to `brain.task_events` (note), `brain.task_external_links` (PR link) and `brain.tasks.status`, one statement each, scoped by task id and `owner_person_id = <me>` with RETURNING; note and link inserts also require status not done and not archived. Repeat check uses `strpos` on a `[sha:...]` or `[pr:...]` marker at the end of the note, over the user's own notes only (`actor_person_id = <me>`); a repeat skips only the note, the PR link and status rule still run. Status rule: event pr with strong evidence moves not_started/in_progress to in_review; `done` only when the user said finished (nothing runs at merge time); blocked and done never change. `me` is `ME_PERSON_ID` in `~/.claude/shared-db-gate.conf` and must be a uuid; while unset the skill reports only, and the gate asks on any UPDATE. The shared-db gate accepts the inserts once `brain.projects` was read in the session, and the status UPDATE when `owner_person_id = <me>` is a top-level AND condition. Not added to the team plugin or the opencode port.

### Saved task per branch and the Brain-Task trailer
`skills/brain-task-sync/brain-task.sh <dir> get|set <id> [--replace]|clear` keeps the Brain task of a branch in local git config `branch.<branch>.brain-task` (short_id digits or a lowercase uuid; common config, so every worktree sees it, never committed, no database access). `set` over a different saved task prints `refused=different-task-saved old=<id>` unless `--replace`; a detached head saves nothing (`detached=true`). `collect-evidence.sh` emits it as `task=<id> source=saved strength=strong` and reads `Brain-Task: <short_id|uuid>` trailer lines (whole line, any key case, optional `#`) as strong in the branch's own commits and in an OPEN PR's body, weak otherwise; a bare number is never a task id. SKILL.md lookup also matches `t.short_id`; a saved or trailer task that differs from the link-derived tasks is ambiguous (no write). git-commit ends every proposed message with `Brain-Task: <id>` when a task is saved (nothing invented otherwise), git-pr adds the same plain line after its links/references lines (else last line), and git-commit, git-push and git-pr put `brain_task` in their envelope result. The agent's report always names the saved task next to the Brain line. brain-story-split step 7 saves the story's short_id for the current branch. No portal URL is documented anywhere in the brain skills or `commands/standup-brief.md`, so none is added. The trailer is not flagged by the public-text gate (its detectors are IP, internal host names, emails and `*-by:` trailers, `_public-text-check.py:208-213`), no-agent-mention (agent-credit patterns only), commit-gate (secret scan, `_commit-gate-check.py:294`) or pr-gate (placeholders come from the template, `_pr-gate-check.py:251-270`), so it is used on every repo.

### Find mode and the saved project
`brain-task-sync` has a read-only event `find`: with no saved task it collects evidence, resolves the project and runs the strong-ref lookup; exactly one not-done, not-archived task is saved for the branch (owner irrelevant), otherwise nothing is saved and candidates are listed with a reason (weak mentions; the user's five most recently updated open tasks in the project, or the project's five most recent with owner names when `ME_PERSON_ID` is unset) and the user is asked. It contains no write and never stops a chain. The git-workflow agent runs it first in every chain that contains git-commit when `brain-task.sh get` prints `task=none`, under the advisory rule, so a branch like `fix/732-thing` gets its trailer in the first commit.

`brain-task.sh <dir> project get|set <uuid>|clear` keeps the repository's Brain project id in git config `brain.project-id` (repo-wide, all worktrees, never committed); `collect-evidence.sh` prints `project=<uuid> source=saved`. The skill's project step reads the saved id (still selecting from `brain.projects` so the shared-db gate sees the project lookup), else looks up by `github_repo`: one row is saved and reported with its `github_project_number`; none lists name/slug candidates and saves only after confirmation; several are listed and none saved. The skill never updates `brain.projects`. brain-locate step 7 saves the project it resolved.

### Rules tightened after review
- Recheck: when brain-task-sync runs with the Brain available and a task is saved, its lookup row is checked; done, archived or owned by someone else is reported in one line (clear it with `brain-task.sh <repo> clear`; the skill never clears it itself). `find` with a saved task still runs the lookup for this, then stops.
- `find` auto-saves only from link-derived strong evidence (`ref=` lines) reaching exactly one not-done, not-archived task. A trailer or uuid with nothing saved (a `task=` line, source not `saved`) is listed first as "named in a commit or PR, confirm" and never saved unasked. With no project resolved there is no candidate query ("no task found, no project").
- Conflicts: the tasks reached by strong evidence of any kind (saved, trailer, link) must be the same single task, else ambiguous and no write; weak evidence is only listed.
- `brain-task.sh set` refuses on the default branch (`main`, `master`, or the `origin/HEAD` branch): `task=none reason=default-branch`, exit 0. Exit codes: 0 for every outcome, 2 for an invalid id, a bad invocation or `set` outside a repo. A missing helper or non-zero exit is reported in one line by git-commit, git-push, git-pr, brain-story-split and brain-locate, which continue as if nothing were saved.
- A saved project id with no row, or whose `github_repo` differs from origin, is cleared and re-resolved; the fallback is brain-locate's own queries (steps 2 and 3), and the skill never runs its step 5 UPDATE.
- git-pr puts `Brain-Task:` in its own paragraph. The agent reads `brain-task.sh get` at report time even when the chain stopped.
- Known limits: `git branch -c` copies the saved task to the new name and a deleted branch can leave an entry behind; the recheck and the report line surface a stale one (characterised in the suite).
